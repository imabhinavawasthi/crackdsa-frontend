# Theory & Concepts

A **Height-Balanced Binary Tree** is a binary tree in which the depth of the two subtrees of *every* node never differs by more than 1.

This property is what keeps search algorithms fast (O(log N)). If a tree becomes unbalanced, it devolves into a linked list, degrading search times to O(N).

### The Brute Force vs. Optimized Approach
**Brute Force (O(N^2)):** For every node, calculate the height of its left child and right child using a helper function. If the difference is > 1, return false. Otherwise, check its children. This is redundant because `height()` calculates heights from scratch every time.

**Optimized Bottom-Up (O(N)):** We can combine the height calculation and the balance check into a single postorder traversal. 
- Ask the left child for its height.
- Ask the right child for its height.
- If either child is unbalanced (returns a sentinel value, typically `-1`), or if the difference between their heights is > 1, the current node is unbalanced (return `-1`).
- Otherwise, return `1 + max(leftHeight, rightHeight)`.

# Common Pitfalls

<Warning>
- **The O(N^2) Trap:** Writing a naive solution that calls a separate `getHeight()` function inside the `isBalanced` recursion. Interviewers will immediately dock points for this.
- **Forgetting to Bubble Up -1:** If the left child returns `-1` (meaning it found an imbalance deep in the tree), you MUST return `-1` immediately to bubble the failure up the call stack.
</Warning>
