# Theory & Concepts
To evaluate a program's performance, beginners often write a quick script that grabs the system clock before and after execution, subtracting the two to print milliseconds. This is known as **experimental analysis**, and it is highly unreliable for several reasons:
*   **Hardware Dependence:** A script that takes 5 milliseconds on a multi-core developer workstation might take 50 milliseconds on a budget smartphone or serverless function.
*   **System State:** Background OS processes, memory paging, and CPU throttling cause execution times to fluctuate wildly between successive runs of the exact same code.
*   **Language & Compiler Differences:** The same logical instructions run at different speeds in interpreted languages like Python compared to compiled languages like C++.

### 1. The Variable Scale: Input Size (N)
Instead of counting milliseconds, we analyze how the number of primitive execution steps grows as the **input size (N)** scales to infinity.
*   `N` represents the size of the data set being processed. For an array sorting algorithm, `N` is the number of elements in the array. For a string lookup, `N` is the length of the string.
*   By focusing on `N`, we look past minor hardware differences and focus entirely on the core efficiency of our code.

### 2. Measuring Growth Curves (The Core Intuition)
Imagine you have two algorithms to search for an item in a list of size `N`:
1.  **Linear Scan (Algorithm A):** Inspects elements one by one. In the worst case, it executes `N` steps.
2.  **Nested Scan (Algorithm B):** Compares every element with every other element. In the worst case, it executes `N * N` steps.

*   If `N = 10`, Algorithm A takes 10 steps, and Algorithm B takes 100 steps. Both are instantaneous.
*   If `N = 100,000`, Algorithm A takes 100,000 steps (instantaneous on a modern CPU). Algorithm B takes 10,000,000,000 steps (takes over 1.6 minutes, hanging the process!).

This scaling behavior is called the **Growth Rate**. We want to select algorithms whose growth rates are as flat as possible as inputs scale.

# Common Pitfalls
<Warning>
- **Testing Only Small Datasets:** Evaluating algorithms with small input sizes (like N=10) and concluding they perform identically. Always test scaling parameters!
- **Relying on Millisecond Timers:** Assuming millisecond time is absolute. Always analyze mathematical instruction cycles instead.
- **Ignoring System Fluctuations:** Forgetting that CPU load, context switches, and thermal throttling will alter milliseconds measurements between successive runs.
</Warning>
