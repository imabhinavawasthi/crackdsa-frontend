# Theory & Concepts
To pass SDE loops, you must think of a technical interview not as an exam, but as a collaborative debugging session between two engineers. The interviewer wants to see how you think, how you handle ambiguity, and how you write clean, production-ready code under pressure.

### 1. The SDE Recruitment Funnel
A standard recruitment process for a mid-to-large product company consists of three main phases:
1.  **Online Assessment (OA):** 60 to 90 minutes. You must solve 2 to 3 algorithmic problems on a platform like HackerRank or Codesignal. These tests are automatically graded, with strict CPU/memory limits.
2.  **Technical Coding Rounds (1 to 3 rounds):** 45 to 60 minutes each. You pair-program with an engineer on a shared virtual editor (like CoderPad) or whiteboard.
3.  **System Design / Behavioral Rounds:** Evaluating your high-level architectural thinking and alignment with the company's culture.

### 2. The Timeline of a 45-Minute Coding Round
A typical virtual coding interview is tightly scheduled. Managing your time is crucial:
*   **00:00 - 05:00 | Introductions:** A brief handshake and background summary.
*   **05:00 - 15:00 | Discussion & Algorithm Design:** The interviewer presents the problem. You ask clarifying questions, dry-run edge cases, state a brute-force approach, and then pitch an optimized O(N) or O(log N) algorithm. **Do not write code yet!**
*   **15:00 - 35:00 | Coding:** Translate your agreed-upon algorithm into clean, modular, syntax-error-free code.
*   **35:00 - 40:00 | Dry Run & Edge Case Checks:** Walk through your code line-by-line using a sample input. Fix any indexing or boundary bugs.
*   **40:00 - 45:00 | Q&A:** Ask thoughtful questions about the team, culture, or technology.

### 3. What Interviewers Actually Evaluate
Your final scorecard is graded on four core pillars:
1.  **Problem Solving:** Can you conceptualize a solution for a vague question, or do you get stuck? Do you notice patterns and optimize naturally?
2.  **Coding Quality:** Is your code modular, dry, and well-structured, with sensible variable names? Do you handle exceptions and pointer bounds safely?
3.  **Communication:** Do you talk through your thought process clearly, or do you code in silence for 20 minutes?
4.  **Verification:** Do you identify bugs on your own using test cases, or do you rely on the interviewer to find them for you?

# Common Pitfalls
<Warning>
- **Coding Immediately:** Jumping straight into writing code the moment the problem is presented. This is the easiest way to fail. If you code the wrong algorithm, you will run out of time to fix it.
- **Silent Coding:** Sitting in silence while coding. The interviewer cannot read your mind and will assume you are struggling.
- **Defensiveness:** Getting defensive or arguing when the interviewer points out a bug. Treat the hint as a cooperative cue and debug gracefully.
</Warning>
