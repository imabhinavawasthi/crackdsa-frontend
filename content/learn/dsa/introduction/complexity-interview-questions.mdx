# Theory & Concepts
Stating "O(N) time and O(1) space" is only 20% of what an interviewer evaluates. They want to hear your reasoning, see how you analyze nested blocks, and observe how you calculate memory allocations. Good communication can secure a 'Strong Hire' recommendation even if your solution has a minor bug.

---

### 1. How Interviewers Frame Complexity Questions
Interviewers will usually prompt you with variations of:
*   *"What is the time and space complexity of your proposed algorithm?"*
*   *"Can we optimize this to use less memory?"*
*   *"What is the worst-case scenario for this approach?"*

---

### 2. The 3-Step Verbal Template (State -> Explain -> Defend)
When explaining complexity, use this structured verbal template:
1.  **State the Bounds:** Give the final answer clearly and immediately:
    *   *“The time complexity is O(N log N) and the auxiliary space complexity is O(N).”*
2.  **Explain the Logic:** Walk through the code line-by-line, pointing out the dominant steps:
    *   *“This is because sorting the input array takes O(N log N) time, and our subsequent single linear scan takes O(N) time. Since O(N log N) dominates, the overall time complexity is O(N log N).”*
3.  **Defend the Space Footprint:** Explain every memory allocation:
    *   *“We declare an extra hash map of size N to store visited elements, resulting in an O(N) auxiliary space footprint.”*

---

### 3. Critical SDE Communication Tips
*   **Define Variables:** If a problem has multiple inputs (e.g. searching a grid of size `R * C` or an array of size `N` and a string of length `M`), always define your variables clearly:
    *   *Bad:* “It takes O(N^2) time.”
    *   *Good:* “Let R be the number of rows and C be the number of columns. The time complexity is O(R * C) because we perform a constant-time search on each cell in the grid.”
*   **Identify the Bottleneck:** Explicitly state which part of your code is the slowest:
    *   *“The bottleneck in my solution is the nested sorting step, which takes O(N log N) time. The rest of the operations are linear.”*

# Common Pitfalls
<Warning>
- **The 'N' Trap:** Assuming every variable is 'N'. Always define what 'N' represents clearly, especially when handling grids or multiple inputs.
- **Rambling:** Giving a long, unfocused explanation before stating the final complexity. State the final bounds immediately, and *then* explain.
- **Ignoring Auxiliary Stack Space:** Forgetting to mention stack memory when discussing recursive solutions. This will instantly signal weak fundamentals.
</Warning>
