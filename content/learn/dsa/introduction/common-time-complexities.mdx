# Theory & Concepts
To analyze software effectively, you must become familiar with the standard **Complexity Classes**. These classes classify algorithms by how they scale as inputs grow. Below is the standard classification, ordered from most efficient to least efficient.

---

### 1. Constant Time: `O(1)`
The runtime does not depend on the input size `N`. The code executes the exact same number of steps regardless of dataset scale.
*   **Examples:** Array index access (`arr[3]`), pushing to a stack, inserting into a hash map (average).
*   **Scale:** Instantaneous.

### 2. Logarithmic Time: `O(log N)`
The algorithm reduces the problem size in half at each successive step.
*   **Examples:** Binary Search in a sorted array, finding items in a balanced Binary Search Tree.
*   **Scale:** Extremely fast. Even if `N` is one billion, `log2(N)` is only ~30 operations!

### 3. Linear Time: `O(N)`
The runtime scales proportionally with the size of the input.
*   **Examples:** Traversing an array, finding the maximum element, counting occurrences.
*   **Scale:** Very fast and highly reliable for standard workloads up to `N = 10^7` operations.

### 4. Linearithmic Time: `O(N log N)`
Slightly slower than linear time. It usually represents a divide-and-conquer strategy where each divide split does linear reconstruction work.
*   **Examples:** Merge Sort, Quick Sort (average case), Heap Sort.
*   **Scale:** Excellent scaling choice for sorting large datasets.

### 5. Quadratic Time: `O(N^2)`
The runtime scales quadratically. Double the input size, and the step count quadruples.
*   **Examples:** Nested loops comparing all pairs (Bubble Sort, Selection Sort, Insertion Sort).
*   **Scale:** Sluggish. Tends to hang when input size `N` exceeds `10,000`.

### 6. Exponential Time: `O(2^N)`
The step count doubles with every single increment of input size `N`.
*   **Examples:** Recursive Fibonacci computation without memoization, generating all subsets of a set.
*   **Scale:** Prohibitive. Even for `N = 40`, the step count exceeds one trillion operations!

### 7. Factorial Time: `O(N!)`
The worst possible complexity class. The runtime grows at an astronomical rate.
*   **Examples:** Solving the Traveling Salesperson Problem via brute force, generating all permutations of an array.
*   **Scale:** Unusable. Even for `N = 15`, operations exceed one trillion!

#include <iostream>
#include <vector>

// Constant Time: O(1)
int getFirstElement(const std::vector<int>& arr) {
    if (arr.empty()) return -1;
    return arr[0]; // Exactly one memory look up step
}

// Logarithmic Time: O(log N)
int binarySearch(const std::vector<int>& arr, int target) {
    int low = 0, high = arr.size() - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2; // Split search space in half
        if (arr[mid] == target) return mid;
        else if (arr[mid] < target) low = mid + 1;
        else high = mid - 1;
    }
    return -1;
}"

# Common Pitfalls
<Warning>
- **Assuming Logarithmic is Linear:** Confusing `O(log N)` with `O(N)`. Logarithmic is significantly faster.
- **Rushing to O(N^2) bubble logic:** Defaulting to nested-loop compares when a simple HashMap precomputation could solve it in O(N) linear time.
- **Overlooking Exponential Scaling:** Attempting to write recursive backtracking without memoization on problems where input size N exceeds 30.
</Warning>
