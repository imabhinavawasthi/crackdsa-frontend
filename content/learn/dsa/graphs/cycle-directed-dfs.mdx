# Theory & Concepts
Detecting a cycle in a **directed graph** is slightly different from an undirected graph. In an undirected graph, encountering an already visited node that is not the direct parent means a cycle exists. However, in a directed graph, finding a visited node does not necessarily imply a cycle (it could just be a cross edge).

For a directed graph, a cycle exists if and only if there is a **back edge**. A back edge is an edge that points from a node to itself or one of its ancestors in the DFS traversal tree.

To keep track of ancestors in the current DFS path, we need to maintain a separate `pathVisited` array (or track nodes in the current recursion stack) along with the standard `visited` array.

### Core Intuition
- Use a `visited` array to keep track of generally visited nodes.
- Use a `pathVisited` array (or `inRecursion` boolean state) to track nodes currently in the recursion stack.
- When visiting a node, mark it in both `visited` and `pathVisited`.
- Explore its adjacent nodes:
  - If an adjacent node is not visited, recursively call DFS.
  - If an adjacent node is **already visited AND is in the `pathVisited` array**, a cycle is detected!
- Backtrack: When returning from the DFS call for a node, unmark it in the `pathVisited` array because we are exiting its path.

# Common Pitfalls
<Warning>
- **Missing path reset:** Forgetting to reset `pathVis[node] = 0` during the backtracking step will lead to false cycle detections across different branches.
- **Using only one visited array:** In a directed graph, standard cycle detection (for undirected graphs) with just a visited array and a parent pointer will fail.
</Warning>
