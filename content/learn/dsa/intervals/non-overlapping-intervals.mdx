# Theory & Concepts
The **Non-overlapping Intervals** problem asks you to find the *minimum number of intervals you need to remove* to make the rest of the intervals non-overlapping.

This problem is functionally identical to the classic **Activity Selection Problem**, which asks for the *maximum number of non-overlapping intervals* you can select. If you find the maximum number of valid intervals, the minimum number to remove is simply the total intervals minus the maximum valid intervals.

### Core Intuition: Greedy Approach
Why greedy? To maximize the number of non-overlapping intervals, we should always pick the interval that **ends the earliest**. The sooner an interval ends, the more room it leaves for subsequent intervals.

1. **Sort by End Time**: Sort the intervals based on their ending times.
2. **Iterate & Count**: Keep track of the `end` time of the last added interval. For each subsequent interval, if its start time is greater than or equal to our tracked `end`, it doesn't overlap! We "keep" it and update our tracked `end`. Otherwise, it overlaps, so we must "remove" it (increment a removal counter).

*Alternative*: You can also sort by start time. If you sort by start time and encounter an overlap, you drop the interval that has the larger end time, as it's more likely to overlap with future intervals. Sorting by end time is mathematically cleaner, though.

                removals++;
            } else {

# Common Pitfalls
<Warning>
- Sorting by start time without updating the end time correctly. If you sort by start time, when overlapping, you must eagerly update your end marker to `min(currentEnd, nextEnd)`. Sorting by end time naturally bypasses this mental hurdle.
- Treating adjacent intervals (e.g., `[1,2]` and `[2,3]`) as overlapping. Typically, in interval scheduling, these do not overlap, so the check should be `<` instead of `<=`.
</Warning>
